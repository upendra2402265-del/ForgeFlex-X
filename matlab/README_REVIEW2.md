# ForgeFlex X — Review 2 Simulink Handoff

## What this layer demonstrates

The Python side produces the forecast, solves the MILP schedule and writes a setpoint file. The Simulink side then acts as the engineering validation layer.

Flow:

`Historical data → Forecast → MILP → 24 h setpoints → Simulink twin → Energy/SOC validation`

## Exact sequence

### 1. In VS Code
From the ForgeFlex project root:

```powershell
python scripts/run_review2.py
```

This creates:

- `review2_outputs/optimized_schedule.csv`
- `review2_outputs/digital_twin_validation.csv`
- `review2_outputs/review2_result.json`
- `review2_outputs/review2_simulink_inputs.mat`

### 2. In MATLAB
Open the project root and run:

```matlab
modelName = build_forgeflex_twin;
```

The script builds:

`ForgeFlex_X_Review2_Twin.slx`

### 3. Run the Simulink model
The model validates the Python schedule using the physical energy-balance relationship:

`Grid + Battery Discharge + PV - Curtailment = Fixed Load + Flexible Load + Battery Charge`

It also integrates battery SOC using the configured charge/discharge efficiencies and checks the configured SOC range through a saturation/observation path.

## What to show a reviewer

1. **Python/Streamlit:** change scenario → run optimizer → show new schedule.
2. **FlexDNA:** show Air Compressor, Chiller and Water Pump shift inside their allowed windows.
3. **Simulink:** show the energy-balance scope close to zero and the SOC trajectory staying within the configured range.
4. **Validation:** show zero production-constraint violations in the numerical twin.
5. **Handoff:** explain that the same optimized setpoints can be forwarded to a future PLC/EMS interface.

## Important honesty point

The Simulink model validates the schedule generated by the numerical optimizer. It does not physically actuate a factory machine. In a deployment architecture, the schedule would be passed to the plant EMS/PLC and then to appropriate control hardware.
